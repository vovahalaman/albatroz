## 1\. Problem

**Input** per panorama:

- One equirectangular 360° JPG, 6080×3040 px.  
- A timestamp `YYYYMMDDhhmmss`, normally part of the filename. Parse with the regex `(\d{14})`.  
- A label: `urban` or `non_urban`.  
- Locations are mainly in Portugal, some in Spain and France. **Islands are included:** Azores, Madeira, Canaries, Balearics, Corsica.  
- Photos are taken in daylight, at ≤5 m above ground, with no human editing. Street names are rare. Some panoramas are taken in open fields, away from roads.

**Output:** a ranked list of **exactly 10 `(lat, lng)` pairs**.

**Scoring per panorama** (from the briefing):

score \= Σ\_{R=1..10} 1000 · 0.95^(R-1) · θ(d\_R) · P\_R

θ\_urban(d)     \= 2 / (1 \+ d/100)

θ\_non\_urban(d) \= 2 / (1 \+ d/10000)

d \= Haversine distance in metres; d \< 10 m is treated as d \= 0

P\_R \= product of penalty factors issued before candidate R (cue ×0.8, MCQ ×0.95, text-only location ×0.5)

"Special One" panorama: ×3

**Human input during the scored run** is limited to two kinds:

- Text cues: ≤1000 characters, with no direct or indirect location reference.  
- Clicks on multiple-choice questions (MCQs) generated by the agent, with ≤4 options.

**Logging:** every AI interaction must be logged as JSON.

**Verified test vectors** (put them in `tests/test_estratega.py`):

| d (m) | 5 | 100 | 500 | 1 000 | 5 000 | 10 000 | 50 000 |
| :---- | :---- | :---- | :---- | :---- | :---- | :---- | :---- |
| θ\_urban | 2.000 | 1.000 | 0.333 | 0.182 | 0.039 | 0.020 | 0.004 |
| θ\_non\_urban | 2.000 | 1.980 | 1.905 | 1.818 | 1.333 | 1.000 | 0.333 |

- Σ 0.95^k for k \= 0..9 \= **8.02526**, so the maximum per panorama is **16 050.5**.  
- Haversine with R \= 6 371 008.8 m: Lisboa (38.7223, −9.1393) → Porto (41.1579, −8.6291) ≈ **274.3 km**.

**Key strategy facts** (verified numerically; they drive Estratega and the MCQ policy):

- **Repeating the single best point 10× maximises expected score.**  
  - The score is a sum with fixed rank weights, so every slot is maximised by the same point.  
  - Example (urban, two far-apart hypotheses with p \= 0.6 / 0.4):  
    - 10× A gives E \= 9 630\.  
    - 5× A \+ 5× B gives E \= 8 230\.  
- **MCQs are cheap verification.**  
  - Example: 4 equally likely far-apart urban candidates give E \= 4 013 without an MCQ.  
  - With one MCQ (×0.95) and 80% human accuracy, E \= 12 198\.

## 4\. Pipeline and state machine

Every stage reads and writes `runs/<pano_id>/state.json`. This lets a run **pause for an MCQ and resume after the click**, which matters because Streamlit reruns the whole script on every interaction.

S0 INGEST       timestamp, label, special\_one, EXIF/XMP probe              → state

S1 VIEWS        lupa.views()                                                → views/\*.jpg

S2 SUN          astrolabio.detect()                                         → state.sun

S3 PERCEIVE     asyncio.gather(leitor, geografo)                            → leitor.json, geografo.json

S4 INVESTIGATE  detetive (tool loop)                                        → detetive.json, state.hypotheses

S5 CRITIC       advogado (P2; skipped if disabled)                          → advogado.json

S6 DECIDE       navegador.decide() → SUBMIT | ASK\_MCQ

                ASK\_MCQ → state.status \= "awaiting\_human" → return

                UI click → navegador.apply\_answer() → S6 again (or S4 if "none of these")

S7 SUBMIT       estratega.submit()                                          → submission.json \+ exports

S8 REPORT       escrivao.export()                                           → log.json, report.md

**Mode `baseline`** (P0): S0 → S1 → baseline agent → geocode its place names → S7 → S8.

**Public API of `core/pipeline.py`** (used by both the UI and the CLI):

def start\_run(pano\_path: Path, label: Label, special\_one: bool, mode: Mode) \-\> str   \# returns pano\_id

def advance(pano\_id: str) \-\> State          \# runs stages until done or awaiting\_human

def answer\_mcq(pano\_id: str, option\_id: str) \-\> State

def add\_cue(pano\_id: str, text: str, override: bool \= False) \-\> CueResult   \# re-enters at S4

def force\_submit(pano\_id: str) \-\> State     \# time budget exhausted → S7 with current hypotheses

**`State` (Pydantic, persisted as JSON):**

- `pano_id`, `pano_path`, `label`, `timestamp`, `special_one`, `mode`  
- `status`: `running | awaiting_human | done | error`  
- `stage`  
- `exif`  
- `sun`  
- `hypotheses: list[Hypothesis]`  
- `mcqs: list[MCQ]`, `cues: list[Cue]`  
- `penalties: list[Penalty]`, `excluded_zones`  
- `submission`  
- `timings`, `token_usage`

**MCQ decision rule** (`navegador.decide`, deterministic; thresholds live in `settings.yaml`):

1. Cluster the hypotheses by Haversine distance (eps: urban 300 m, non-urban 5 km). Cluster weight \= sum of member weights, normalised.  
2. Ask only if **all** of these hold:  
   - `mode == assisted`;  
   - fewer than `max_mcq_per_pano` (2) MCQs have been asked so far;  
   - at least 2 clusters are farther apart than `mcq_far_m` (urban 1 000 m, non-urban 30 000 m);  
   - the top cluster weight is \< 0.6;  
   - the top 3 clusters together are \> 0.7.  
3. Options: the top ≤3 clusters, each described by the reverse-geocoded zone name, plus "none of these". The LLM (`prompts/navegador.md`) phrases the question and the option texts.  
4. Applying the answer:  
   - The chosen cluster gets weight `q_trust` (0.85). The others share the remainder.  
   - "None of these" → add those zones to `excluded_zones` → re-run S4.

Label \= Literal\["urban", "non\_urban"\]; Mode \= Literal\["baseline", "autonomous", "assisted"\]

## 8\. LLM layer (`llm.py`) — verified against `google-genai` 2.29.0

**Client.** `genai.Client(vertexai=True, project=PROJECT, location="global")`.

- 2.29.0 also accepts `enterprise=True`. Both work. Env equivalents: `GOOGLE_GENAI_USE_VERTEXAI=true`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`.  
- Auth: `gcloud auth application-default login`.  
- Fallback: `genai.Client(api_key=GEMINI_API_KEY)` if `.env` sets it and Vertex fails.

**Smoke test** `uv run python cli.py check-llm`:

1. `client.models.list()` → print the model names that contain "gemini".  
2. One text call.  
3. One image call (`types.Part.from_bytes`).  
4. Print latency and `response.usage_metadata`.

The team picks the model IDs for `settings.yaml` from this output.

**Signature:**

async def call(role: str, prompt\_file: str, \*, pano\_id: str, text\_parts: Sequence\[str\] \= (),

               images: Sequence\[ImageRef\] \= (), schema: type\[BaseModel\] | None \= None,

               tools: Sequence\[Callable\] | None \= None, max\_tool\_calls: int | None \= None) \-\> LLMResult

`ImageRef = (path, media_resolution)`. `LLMResult` carries `text`, `parsed`, `tool_calls`, `usage`, `latency_s` and `model`.

**Implementation facts (verified fields):**

- **System prompt:** `types.GenerateContentConfig(system_instruction=<prompt file body>)`.  
  - Prompt files may have YAML front-matter `knowledge: [regional_cues.md, ...]`. Those knowledge files are appended to the system instruction.  
- **Images:** `types.Part.from_bytes(data=..., mime_type="image/jpeg")`. `Part` has a `media_resolution` field, and the config has `media_resolution` too (`types.MediaResolution.MEDIA_RESOLUTION_LOW|MEDIUM|HIGH`).  
  - Gemini 3 cost per image: LOW 280 · MEDIUM 560 · HIGH 1 120 tokens.  
- **Structured output:** `response_mime_type="application/json"` \+ `response_json_schema=Schema.model_json_schema()`. Then `Schema.model_validate_json(resp.text)`. On a validation error, retry once with the error message appended.  
- **Tool loop:** pass typed Python functions with docstrings in `tools=[...]`. Configure `automatic_function_calling=types.AutomaticFunctionCallingConfig(maximum_remote_calls=N)`.  
  - **Do not combine tools with `response_json_schema`** in the same call; that combination is not reliably documented. Agents with tools return results through a tool (see Detetive).  
- **Async:** `client.aio.models.generate_content(...)` (automatic function calling also exists in the async path). Use async for parallel perception. A sync call inside `asyncio.to_thread` is fine for the Detetive.  
- **Thinking:** `types.ThinkingConfig(thinking_level=...)` only if `settings.thinking_level` is set.  
- **Retries:** `tenacity` with exponential backoff on 429/500/503, max 4 attempts. Timeout from `budgets.llm_timeout_s`.  
- **Logging:** every call emits one `llm_call` event (§11) with:  
  - role, model, prompt file path \+ git short hash;  
  - full text parts;  
  - images as `{path, sha256, media_resolution}` (**never base64**);  
  - raw response text, parsed JSON, tool calls (name, args, result summary);  
  - `usage_metadata`, latency.

## 9\. Tools

### 9.1 `lupa.py` (conventions verified with py360convert 1.0.4)

- `py360convert.e2p(img, fov_deg, u_deg, v_deg, out_hw)`:  
  - **`u_deg` \> 0 looks right** of the image centre column.  
  - **`v_deg` \> 0 looks up.**  
  - About 0.35 s per 1024² view.  
- **Image yaw convention:** yaw 0 \= centre column, positive to the right, range (−180, 180\]. **This is not compass north.**  
- `pixel_to_angles(x, y, W, H)`: `yaw = (x/W − 0.5)·360`, `pitch = (0.5 − y/H)·180`.  
- `views(pano_path, out_dir) -> list[View]`:  
  - `h000…h315`: 8 horizontal views, yaw 0,45,…,315 mapped to (−180,180\]; pitch 0; FOV 90; 1024².  
  - `g000,g090,g180,g270`: ground views, pitch −50.  
  - `overview.jpg`: equirect resized to 2048×1024.  
  - Each `View` has `name`, `yaw`, `pitch`, `fov`, `path`.  
- `zoom(pano_path, yaw, pitch, fov, size=1024) -> Path`: FOV clamped to 8–90. Cached by parameters.  
- Tests:  
  - A white square drawn at (yaw \= 90, pitch \= 0\) appears at the centre of the view with `u=90` and is absent at `u=−90`.  
  - A square at pitch \+30 is centred in the view with `v=30`.

### 9.2 `astrolabio.py` (`pvlib.solarposition.get_solarposition`, `timezonefinder.TimezoneFinder`)

- `detect(pano_path) -> SunObs | None`:  
  - Downscale to 1520×760.  
  - Upper half only.  
  - Threshold near-saturated luminance; take the largest compact connected component.  
  - Centroid → `pixel_to_angles` → `{yaw, elevation, area_px, confidence}`.  
  - Return `None` if nothing plausible is found.  
- `sun_check(lat, lng, timestamp, sun_yaw=None, sun_elev=None) -> dict`:  
    
  - Find the time zone with `timezone_at(lat=, lng=)`.  
      
  - Localise the naive timestamp as local time (`flags.timestamp_is_local`, **\[CONFIRM\]**), else UTC.  
      
  - Return `{expected_elev, expected_azimuth, elev_residual, north_offset_yaw}`, where `north_offset_yaw = sun_yaw − expected_azimuth` (normalised). That is the image yaw that points north.  
      
  - Sanity reference, 2026-10-10 14:00 local:  
    

| Place | Elevation | Azimuth |
| :---- | :---- | :---- |
| Lisboa | 43.7° | 192.6° |
| Madrid | 42.8° | 179.4° |
| Funchal | 50.6° | 182.1° |

    

    Note how the time zone shifts the azimuth.


- (P2) `band(timestamp, sun_elev, tol=2.0) -> list[(lat,lng)]`: 0.25° grid over the regions.

### 9.3 `geo.py` — Detetive tool functions (typed, docstrings, cached on disk, logged)

Every result dict includes a `call_id` (short hash), which is registered in the run's tool registry.

- `geocode(query: str, country_codes: str = "pt,es,fr", limit: int = 5) -> list[dict]` — Nominatim `/search`.  
- `reverse(lat: float, lng: float, zoom: int = 14) -> dict` — Nominatim `/reverse`.  
- `overpass_near(lat: float, lng: float, osm_tag: str, radius_m: int = 500) -> list[dict]` — e.g. `amenity=place_of_worship`. Result cap 50\. Timeout 25 s.  
- `overpass_named(name: str, bbox: str | None = None) -> list[dict]`  
- `wiki_coords(query: str, lang: str = "pt") -> dict | None` — Wikipedia search \+ coordinates.

**Nominatim usage policy** ([https\://operations.osmfoundation.org/policies/nominatim/](https://operations.osmfoundation.org/policies/nominatim/)):

- **Maximum 1 request/s for the whole application.** This applies to all four laptops together, so keep volume low (`max_geocode_calls_per_pano`).  
- Use a custom User-Agent with a contact address.  
- Cache every response.  
- No bulk or grid queries, no autocomplete.

### 9.4 `estratega.py`

- `haversine_m(a, b)`, `theta(d, label)` (d \< 10 m → 0), `score(cands, truth, label, penalty_factors_per_rank)`.  
- `expected_theta(point, hypotheses, label, samples)`:  
  - Draws a Monte Carlo sample from a mixture of isotropic Gaussians (σ \= `radius_m`, weights normalised).  
  - Returns the mean θ.  
- `best_point(hypotheses, label) -> (lat, lng, e_theta)`:  
  - Candidates \= hypothesis centres \+ a local grid around the top 3 (`grid_step_m`).  
  - Picks the argmax. Uses a fixed RNG seed so results are deterministic.  
- `submit(state) -> Submission`:  
  - `ev` (default): 10 × best point.  
  - `hedge`: best point on ranks 1–5, best point of the second cluster on 6–10.  
  - With no hypotheses: centroid of the Geógrafo's top region (geocoded), else `fallback_point`.  
  - Penalty factor \= product of `state.penalties`. `expected_score` \= 1000 · Σ w\_R · E\[θ\] · P\_R · (3 if special\_one).  
- Tests:  
  - θ table and max score from §1.  
  - `ev` returns 10 identical pairs.  
  - Always 10 valid pairs, also with an empty hypothesis list.  
  - With two far clusters weighted 0.6/0.4, the best point lies in the 0.6 cluster.

## 10\. Agents (prompt \+ schema contracts)

**Every prompt file has:**

- front-matter `knowledge: [...]`;  
- the role;  
- the procedure;  
- "separate observation from inference; confidence 0–1; never invent";  
- the output description;  
- one short example.

Agent `.py` files stay under \~80 lines. The logic lives in the prompts.

**Baseline (P0)** — `BaselineResult`

{"country\_probs":{"pt":0,"es":0,"fr":0},

 "places":\[{"query":"geocodable place string","country":"pt","confidence":0.0,"why":"..."}\],

 "clues":\["..."\]}

- Input: overview (LOW) \+ 8 horizontal views (MEDIUM) \+ label \+ timestamp.  
- The code geocodes the top 3 `places[].query` via `geo.geocode`. Each result becomes a `Hypothesis` with:  
  - provenance \= that `call_id`;  
  - weight \= confidence;  
  - radius \= 300 m (urban) or 8 km (non-urban).  
- Draft prompt in Appendix B.

**Leitor** — `LeitorResult`

{"texts":\[{"text":"...","view":"h090","kind":"sign|shop|plate\_format|phone|domain|other","language":"pt|es|fr|gl|ca|eu|other","confidence":0.0}\],

 "language\_verdict":{"pt":0,"es":0,"fr":0,"other":0},

 "search\_terms":\["..."\],

 "zoom\_requests":\[{"yaw":0,"pitch":0,"fov":20,"why":"..."}\]}

- Pass 1: 8 views → result including `zoom_requests` (max 6).  
- The code renders the zooms (HIGH).  
- Pass 2: the zoom crops \+ pass-1 JSON → merged final result.

**Geógrafo** — `GeografoResult`

{"observations":\[{"cue":"vegetation","value":"...","view":"h135","status":"observed|not\_observed|uncertain","confidence":0.0}\],

 "region\_guesses":\[{"region":"...","country":"pt","prob":0.0,"why":"..."}\],

 "water\_or\_coast":{"present":false,"yaw":null,"type":null},

 "terrain":"...","season":"..."}

Works through `knowledge/regional_cues.md` as a checklist.

**Detetive** — tool loop. Tools:

- `geocode`, `reverse`, `overpass_near`, `overpass_named`, `wiki_coords`, `sun_check`  
- **`add_hypothesis(lat, lng, radius_m, weight, label, provenance, evidence, why)`**

`add_hypothesis` validates `provenance` against the tool registry (R2) and appends to `state.hypotheses`.

- Input: Leitor \+ Geógrafo JSON, `state.sun`, cues, MCQ answers, `excluded_zones`, label-specific guidance:  
  - urban: street-level, radius ≤150 m;  
  - non-urban: region-level, radius 2–20 km.  
- Final text: a short summary, saved to `detetive.json` together with the hypotheses.

**Navegador (phrasing)** — `MCQ` JSON: question \+ options (ids `A`–`D`).

**Cue guard** — `{"references_location": bool, "why": str}`.

- Flash-Lite.  
- If flagged, the UI blocks the cue. Sending it anyway requires an explicit override, and the override is logged.

**Advogado (P2)** — `{"objections":[{"hypothesis_label","issue","severity"}],"weight_multipliers":{"<label>":0.5}}`.

**Professor (P2)**

- Input: `runs/<id>/log.json` \+ `review.md`.  
- Output: a markdown diff proposal for `knowledge/lessons.md` and `confusion_pairs.md`. **General rules only, never "panorama X is in Y".**

## 14\. Evaluation and learning loop

1. `batch` over the training panoramas. Every run is saved, including the git commit.  
2. Human review per panorama:  
   - Check plausibility in maps / Street View.  
   - Write `runs/<id>/review.md` (decisive clue, misleading clue, verdict).  
   - If the team is reasonably sure, add a row to `eval/labels.csv` (`filename,label,lat,lng,confidence,reviewer`).  
3. `eval/compare.py` reports, per mode (baseline vs. crew) and per git commit:  
   - pseudo-score (Estratega `score` vs. `labels.csv`);  
   - median distance and country accuracy;  
   - time and tokens.  
4. `learn` → Professor proposal → team approves → commit to `knowledge/`.  
5. Before the scored run, tag the repo `freeze-sunday`.

## Appendix B — draft `prompts/baseline.md`

\---

knowledge: \[regional\_cues.md, confusion\_pairs.md\]

\---

You are an expert geolocation analyst. You receive one 360° panorama as an overview image

plus 8 perspective views (h000…h315; yaw relative to the image centre, NOT compass north),

the capture timestamp (local time) and a label (urban / non\_urban).

The location is mainly in Portugal, sometimes Spain or France, including islands.

Procedure:

1\. List concrete observations (text, signs, architecture, vegetation, terrain, infrastructure). Mark each as

   observation, not inference.

2\. Infer country probabilities (pt, es, fr) and explain which observations drive them.

3\. Propose up to 5 candidate places as \*\*geocodable query strings\*\* (e.g. "Rua Augusta, Lisboa",

   "Monsaraz, Évora"). For urban panoramas aim for street or landmark level; for non\_urban a village,

   parish or natural feature is fine.

4\. Give each a confidence (0–1). Confidences need not sum to 1\. Prefer fewer, well-supported places.

Rules: never output coordinates; never invent text you cannot read; if unsure, say so via low confidence.

Return JSON matching the provided schema only.
